# 跑通“带参数命令绑定到 Type 并在有/无 Layer 4 数据库下表现不同”的分析报告

本报告针对当前插件的代码结构，分析其在将带参数命令绑定到 Type（Layer 3）时，对于**无 Layer 4 数据库**和**有 Layer 4 数据库**两种场景下的参数解析支持度，解释配置层级的设计选择，并明晰变量替换的优先级规则。

---

## 一、 当前设计结构支持度分析

### 1. 无 Layer 4 数据库（纯编辑器块）
* **结论**：**完美支持**。
* **工作流**：
  - 当一个块（如带有 `#Project` 标签的普通块）被触发菜单时，其绑定的命令参数解析在 [command-dispatcher.ts](file:///Users/feng/Desktop/项目/思源项目/siyuan-plugins-index/src/features/command/command-dispatcher.ts#L242-L283) 的 `buildParams` 中处理。
  - **自身参数自动传递**：
    - **上下文注入 (`injected` 参数)**：系统会自动从 DOM 触发上下文中提取 `blockId` 并填入参数。
    - **模板解析 (`template` 参数)**：`resolveTemplate` 能够实时计算并替换 `{{block_id}}`, `{{date}}`, `{{time}}`, `{{parent_id}}` 以及 `{{root_id}}`。
    - **块级属性解析**：通过 `{{attr:KEY}}` 语法，Dispatcher 会发起 `/api/attr/getBlockAttrs` 请求，直接提取块自身已有的自定义属性值并注入执行。

### 2. 有 Layer 4 数据库（块已加入 Attribute View 属性视图）
* **结论**：**部分支持（需通过思源底层属性通道转换），但缺乏直接基于本地 SQL 数据库列名的解析**。
* **工作流**：
  - **思源官方通道（可用）**：思源官方会将属性视图（AV）中每一列的单元格值，以自定义属性（通常是 `custom-av-[keyId]`）的形式写入该块的属性中。这意味着用户若在命令的参数映射中填写 `{{attr:custom-av-[keyId]}}`，仍然可以取得数据库中的列值，从而实现不同的执行效果。
  - **局限性**：当前的 Dispatcher 并没有与本地 SQLite 数据库打通以进行“列名到属性值”的直接翻译。用户无法在参数中直接使用 `{{Status}}` 或 `{{attr:Status}}`（即直接使用友好的数据库列名）来获取 Layer 4 的值。

---

## 二、 核心问题解答

### 1. 当前参数/字段名在何处配置？应该在何处配置？

* **当前现状**：
  - 当前参数的字段映射是在 **Layer 2 (Command-DB / `sys_command_db` 的 `Param_Mapping` 字段)** 完成配置的。
  - **Layer 3 (Type-DB)** 只进行 Supertag 与命令名称的绑定关系建立，而不干涉参数映射的具体配置。
* **架构建议：它应当在 Layer 2 完成配置**。
  - **原因**：
    1. **命令复用**：一个带有复杂参数映射的命令可以被多个不同的 Type (Layer 3) 重复绑定。如果将配置挪到 Layer 3，每次绑定都需要为每个 Supertag 重新写一遍繁琐的参数 JSON，造成数据冗余与维护困难。
    2. **职责划分**：
       - **Layer 2 (Commands)** 负责“如何执行该命令（What & How）”，决定具体的参数占位符应该取自哪些数据列。
       - **Layer 3 (Type)** 负责“在何处触发命令（Where）”，仅仅作为按钮与超级标签的关联纽带。

---

## 三、 参数解析优先级设计规则

当一个命令在解析模板占位符（例如 `{{Status}}`）时，为保证多数据库共存块的数据正确性，我们将遵循以下**优先级规则**进行数据读取：

```mermaid
graph TD
    A[开始解析 {{Status}}] --> B{该块是否存在于<br>与当前 Type 同名的 Layer 4 表中?}
    B -- Yes --> C[优先级 1: 读取同名表中的该列值]
    B -- No --> D{该块是否存在于<br>其他 Layer 4 表中?}
    D -- Yes --> E[优先级 2: 读取其他表中的该列值]
    D -- No --> F[优先级 3: 读取块自身的自定义属性/上下文默认值]
```

### 1. 优先级 1：同名 Layer 4 数据库（与当前 Type 同名）
* **场景**：当前触发的 Supertag 是 `#Project`，如果检测到本地 SQLite 中存在一个名为 `Project` 的表（即 Layer 4 数据库），且该表中包含当前 `blockId`，则优先从该表中读取字段 `Status`。
* **理由**：同名数据库与超级标签在业务逻辑上是强绑定的主从关系，数据最精准。

### 2. 优先级 2：其他 Layer 4 数据库
* **场景**：若块被多重继承或收录于其他数据库（如 `Task` 数据库），但当前并没有与 Type 同名的数据库时，检索其他包含此 `blockId` 的 Layer 4 表并读取其列值。

### 3. 优先级 3：其他（属性或默认值）
* **场景**：若该块未加入任何 Layer 4 本地 SQLite 数据表，则退回到思源的块属性（Attributes）中读取，或者使用系统默认上下文（Context/Default）数据。
