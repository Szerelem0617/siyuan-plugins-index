# SOT (Single Source of Truth) 与数据绑定深度规划

在思源插件索引与属性继承功能的演进中，我们面临着核心数据归属权的挑战。目前，我们的系统中存在三种可能具备状态的实体：

1. **List (列表块)** : 用户最初输入文档大纲的地方。
2. **Page (文档/页面)** : Builder 基于列表生成的子文档。
3. **DB (数据库/Attribute View)** : 附着在列表或页面上，用于管理属性的视图。

为了确保这三者在各种组合下都能保持数据一致性且逻辑不至于过于复杂，我们需要明确谁是 **Single Source of Truth (唯一真实数据源, SOT)** 。

## 一、 现状分析与痛点

1. **组合复杂性**：用户的使用场景千变万化。

   - 场景 A：仅仅使用 List 生成了子 Page（无数据库）。
   - 场景 B：在 List 上建了 DB，但没有生成子 Page（纯属性管理）。
   - 场景 C：List 既生成了 Page，又绑了 DB（最复杂的完全体）。
2. **冗余的 Icon 列**：当前我们在 DB 中手动维护了一个 `Icon` 列以支持继承。其实思源的原生数据库（主键列）以及关联页面本身就有 Icon 属性，如果在主键/页面上修改，思源底层会自动级联。我们自己维护 Icon 导致逻辑重叠且容易冲突。
3. **反向同步冲突**：当非 SOT 的实体被用户手动修改时（例如：DB 是 SOT，但用户直接在 List 上手改了 Icon 或文本），插件该如何反应？

---

## 二、 核心决策提案

### 决策 1：维持自建 Icon 列

维持现有设计，继续使用自定义的 `icon` 属性列。该列作为标准属性在 DB 中管理，支持提取 List 首个 Emoji 作为初始值。

### 决策 2：SOT 的确立 (分类权威制/多元真理)

为了确保逻辑清晰，我们根据数据维度划分权威性：

**1. 位置层级 (Hierarchy & Position) → SOT: List (列表大纲)**
**2. 结构化属性 (Structural Attributes) → SOT: DB (属性视图)**
**3. 最终呈现 (Render/View) → Page (生成的页面)**

#### 为什么 List 是位置关系的绝对 SOT？

1. **物理结构决定论**：思源笔记的文档树结构本质上是由列表（List）的嵌套关系决定的。
2. **DB 的局限性**：虽然我们在 DB 中同步了 `Father`、`Path` 和 `Level` 字段，但**直接在 DB 中修改这些字段是无效的**。即使手动改了文本值，插件也无法推断出块在物理文档树中的精确相对位置（例如插入到哪个兄弟节点之后）。因此，List 是位置关系的唯一真相来源。
3. **分发策略**：一旦发生冲突，层级属性总是“**从 List 提取并覆盖 DB**”。

#### 为什么 DB 是属性元数据的绝对 SOT？

1. **管理优势**：DB 提供了强大的多维视图，是集中管理、批量修改状态、标签、数值等 Meta 信息的最佳场所。
2. **分发策略**：对于非层级相关的自定义属性，总是“**以 DB 为准向 Page/IAL 分发覆盖**”。

#### 场景详述与同步策略：

 **【场景 A】：List + Page (无 DB)**

- **SOT**: **List (列表)** 。修改应以 List 为准向下刷新 Page。

 **【场景 C】：List + Page + DB (完全体)**

- **分工联动**：
  - **位置/层级/文本内容**：用户在 List 中拖拽块或修改正文。由于 List 是 SOT，其变动会自动计算并同步至 DB（更新 `Father` / `Path` / `Level` / `ID` 等）。
  - **元数据 (Status/Tags/Properties)**：用户在 DB 视图中交互。由于 DB 是属性 SOT，修改后会自动触发相关块的 IAL 属性同步或向下游继承同步。

---

## 四、 下一步执行建议 (Action Items)

1. **Icon 功能闭环**：在 `db-config.ts` 中增强对 `icon` 列的处理，确保在修改该列时，能有选择地同步回块的 `icon` 属性（IAL）。
2. **自动同步监听 (Auto-Sync)**：
   - **监听 DB 变更**：通过 `ws-main` 监听 `transactions`，识别 `action: "setAttrViewColVal"` 且作用于已绑定 DB 的操作。
   - **属性回刷 (IAL Sync)**：当 DB 中的 `icon` 或 `level` 等字段发生手动修改时，自动执行 `setBlockAttrs` 更新对应的块属性，保持双向一致。
   - **下游继承同步 (Inheritance Sync)**：若修改的字段配置了“强继承 (Strong Inheritance)”，自动触发其所有子项（Children Rows）在 DB 中的对应单元格更新。
3. **性能优化**：由于 `transactions` 频率较高，自动同步需要配合 `debounce` (防抖) 机制，避免频繁请求 API 导致界面卡顿。
4. **清理遗留代码**：彻底移除之前尝试切换原生主键图标时的实验性代码。
