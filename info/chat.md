# SOT (Single Source of Truth) 与数据绑定深度规划

在思源插件索引与属性继承功能的演进中，我们面临着核心数据归属权的挑战。目前，我们的系统中存在三种可能具备状态的实体：
1. **List (列表块)**: 用户最初输入文档大纲的地方。
2. **Page (文档/页面)**: Builder 基于列表生成的子文档。
3. **DB (数据库/Attribute View)**: 附着在列表或页面上，用于管理属性的视图。

为了确保这三者在各种组合下都能保持数据一致性且逻辑不至于过于复杂，我们需要明确谁是 **Single Source of Truth (唯一真实数据源, SOT)**。

## 一、 现状分析与痛点

1. **组合复杂性**：用户的使用场景千变万化。
   - 场景 A：仅仅使用 List 生成了子 Page（无数据库）。
   - 场景 B：在 List 上建了 DB，但没有生成子 Page（纯属性管理）。
   - 场景 C：List 既生成了 Page，又绑了 DB（最复杂的完全体）。
2. **冗余的 Icon 列**：当前我们在 DB 中手动维护了一个 `Icon` 列以支持继承。其实思源的原生数据库（主键列）以及关联页面本身就有 Icon 属性，如果在主键/页面上修改，思源底层会自动级联。我们自己维护 Icon 导致逻辑重叠且容易冲突。
3. **反向同步冲突**：当非 SOT 的实体被用户手动修改时（例如：DB 是 SOT，但用户直接在 List 上手改了 Icon 或文本），插件该如何反应？

---

## 二、 核心决策提案

### 决策 1：关于 Icon 的全面退让 (Embrace Siyuan Native)
**废弃自定义的 `Icon` 属性列。**
思源笔记在这方面做得很完美：如果数据库（AV）的主键关联了一个块/页面，当你改变页面的图标时，AV 主键图标会自动更新；反之亦然。我们不需要（也不应该）自己去拦截和同步 Icon。
- **改动计划**：移除代码中所有对 `Icon` 的特殊硬编码检索和继承同步。把图标的管理权完全交还给思源原生机制。

### 决策 2：SOT 的动态降级转移机制
我们必须确立一条明确的 **“权力链 / 优先级 (Hierarchy of Truth)”**，而不能采用平级双向绑定（平级双向极易导致死循环和各种竞态条件冲突）。

**SOT 优先级： DB (属性视图)  >  Page (生成的页面)  >  List (列表本身)**

#### 场景详述与策略：

**【场景 A】：List + Page (无 DB)**
- **SOT**: **Page (页面)**。
- **逻辑**：一旦 List 生成了 Page，Page 就成为了真实内容和属性的主宰。
- **用户行为响应**：
  - 用户修改 Page 标题/引文 -> `List` 应该自动更新（通过原生 Embed 或我们写逻辑反向同步）。
  - 用户独立修改 List 文本 -> 理论上这种行为应该被阻止或覆盖，最好强制 List 变为一个原生的 `((Block Ref))` 或 `{{Embed}}` 块，把修改全部逼迫到 Page 上发生。

**【场景 B】：List + DB (无 Page)**
- **SOT**: **DB (属性视图)**。
- **逻辑**：数据库接管了该列表项的附加元数据。
- **用户行为响应**：
  - 用户在 DB 中修改属性 -> 属性储存在 DB 数据中。
  - 用户在 List 上直接通过原生属性面板修改对应 key 的值 -> 由于 DB 是 SOT，插件应立刻检测到并更新 DB，或者每次 DB 重新加载时覆盖 List。*（最佳实践：单向绑定，让 DB 重写 List 的 IAL；如果你想支持类似 Notion 的双向编辑，你需要监听块属性变更事件立刻写回 DB）*。

**【场景 C】：List + Page + DB (完全体)**
- **终极架构建议：换绑 DB 到 Page 主键上**。
- **逻辑分析**：既然 Page 是内容的 SOT，DB 是属性的 SOT，如果 DB 绑在 List 上，那三者就形成了一个混乱的三角关系。
- **解决方案**：当用户对一个已经绑定了 DB 的 List 执行 "Build Page (生成子向导)" 时，插件在后台**自动将该 DB 行的关联主键，从 List Block ID 转移到新生成的 Page Block ID 上**。
- **结果**：列表 (List) 彻底降级为一个单纯的“目录大纲视图”（甚至是原生 Embed 视图）。所有的属性修改、内容修改全部集中在对应的 Page 和关联该 Page 的 DB 上。这不仅逻辑统一，而且对于用户来说极其清晰（点开页面，页面的属性面板和视图属性是一致的）。

## 三、 反向编辑策略 (What if the user edits the non-SOT?)

设定了 SOT 之后，不可避免用户会去编辑被降级的实体（比如在完整的场景 C 里，他没有点进去 Page，而是在最外层直接去改了原先那个 List 块的文字）。

**我们的策略：最终一致性 (Eventual Consistency with Strict UI feedback)**

1. **对内容 (Text/Title) 的反向编辑**：
   如果 List 被转换为了 `{{Embed}}` 或者 `((Ref))` 形式，用户很难不经意间在原地改大面积文本。如果他硬改了文本，思源原生就会把它变成一个普通块。此时如果我们检测到链接断裂，可以将他视为一个全新的独立节点，不再参与原有的自动同步，直到他重新执行 Builder 建立映射。
2. **对属性 (Attributes/IAL) 的反向编辑**：
   如果 SOT 是 DB：
   - 当检测到 List IAL 被外部（非 DB UI）修改：插件立刻抓取这个更新 (`ws-main update`)，去对比和重写关联的 DB 行。这也就是相当于“把 DB 作为集中显示的面板，但也允许原生属性入口作为输入”。一旦写入 DB，DB 再次作为 SOT 向下广播物化计算。
   - 这也是最不让用户迷惑的方法。用户改哪里都有效，但底层数据最终汇集到 DB，以 DB 的计算结果为准再刷回页面。

---

## 四、 下一步执行建议 (Action Items)
1. **清理阶段**：彻底移除代码中所有关于自定义 `Icon` 的继承和读写逻辑。
2. **关系梳理**：修改 Builder 逻辑。检测如果当前 List 已经处于某个 DB 中，在生成 Page 的同时，调用思源 API 将 DB 中的对应记录绑定的 ID 更新为新生成的 Page ID。
3. **拦截降级**：将 Builder 生成出来的 List 项尽可能替换为只读或链接（原生 Ref/Embed）的展现形式，从产品设计上阻止“多头写”的情况。
