# 数据库属性继承方案：深度总结与优化分析

## 1. 当前实现方案总结 (Materialized Top-Down Sync)
目前我们采用了 **“构建时物化同步”** 的方案：
- **触发时机**：在“文档构建器”执行或“自动更新”触发时。
- **逻辑模型**：自顶向下递归。在处理每一层列表项时，结合其本地数据库属性与父级已解析出的“继承快照”进行合并（Weak/Strong 逻辑）。
- **持久化**：将解析后的最终值直接写入对应文档的 `IAL` (属性) 中。

### 优点
- **读性能极致**：文档打开时，属性已经是计算好的字符串，无需任何二次计算或查询数据库。
- **解耦**：文档一旦生成，不再强依赖数据库的实时存在，具有更好的离线访问和迁移能力。

### 缺点
- **同步滞后**：如果只修改了数据库中的父级属性，未触发构建器更新，子文档的 IAL 不会自动变。
- **数据冗余**：每个子项都存储了一份副本。

---

## 2. 效率评估：是否达到了“极致高效”？
**结论：在“文档展示”层面是极致的，但在“数据管理和实时查询”层面仍有提升空间。**

目前在 `builder.ts` 中的实现瓶颈：
1. **全量加载**：`getColIDMap` 每次都会拉取整个数据库的键值对。虽然有 `avCache` 减少了单次任务内的重复请求，但对于包含数千条记录的大型数据库，JSON 解析和内存占用较高。
2. **递归解析**：虽然 $O(N)$ 的复杂度在前端可以接受，但如果数据库层级极深且规则复杂，同步过程会有明显的 UI 阻塞。

---

## 3. 更高维度的可能的优化方案

### 方案 A：虚拟动态解析 (Virtual Read-time Inheritance)
不在 IAL 存值，而是在查询数据库或渲染文档时，动态溯源。
- **原理**：修改 API 请求，在获取结果后，通过 JavaScript 在内存中快速递归 `parentMap` 填充空值。
- **适用场景**：对实时性要求极高，且数据变动极其频繁的场景。

### 方案 B：响应式物化 (Reactive Materialized View)
通过监听思源的属性变更事件（如果有），自动向下传播。
- **原理**：当检测到某个块的 IAL 变更且该块在某个 AV 中，自动触发其所有后代的属性更新。
- **适用场景**：真正把思源当成关系型数据库使用的用户。

---

## 4. 最推荐方案：基于 Tree-Snapshot 的增量物化 (Incremental Tree-Sync)

这是我认为最平衡、最能体现“极致”的方案，建议未来迭代方向：

### 核心策略：
1. **树状快照索引**：
   在内存中维护一个轻量级的 `id -> {parent, values}` 的扁平化树结构索引。
2. **按需字段加载**：
   不通过 `getAttributeView` 获取所有数据，而是通过 SQL 仅查询 `custom-index-db-config` 中涉及继承的特定列。
3. **计算缓存 (Memoization)**：
   在 `resolveInheritance` 中引入全局 Memo。如果父项的解析结果已计算，子项直接引用内存指针，不再重新执行逻辑判断。
4. **延迟写入 (Batch Commit)**：
   现在的实现是边解析边 `setBlockAttrs`。极致高效的做法是：在递归完成后，对比旧 IAL，仅对真正发生变化的块进行 **一次性批量事务提交**。

### 总结建议：
对于插件目前的定位，**当前的“构建时自顶向下传递”已经是逻辑上最清晰且性能优异的实现**。我们通过将 $O(N \times D)$ 的回溯查询优化为了 $O(N)$ 的状态传递，已经避开了最大的性能坑。

**后续优化优先级：**
1. **批量写入**：将所有 `setBlockAttrs` 收集起来，通过 `api/transactions` 一次性提交，减少网络往返。
2. **脏检查 (Dirty Check)**：在写入 IAL 前对比值，如果没有变化（如 Weak 继承且本地已有值）则跳过 API 调用。

---

## 5. 响应式同步的深度思考 (Reactive Sync Deep Dive)

针对思源笔记缺少直接“属性钩子”的问题，结合最新的内核调研，我们对“方案 B：响应式物化”有了更清晰的落地路径：

### 5.1 技术切入点：WebSocket 监听器
目前最可行且高效的实时同步方式是 **订阅 `/ws` 接口的 `transactions` 消息**。
- **机制**：监听 `doOperations` 数组中 `action: "setAttrs"` 的动作。
- **逻辑分析**：
  1. 捕获 `id` (变更块) 和 `data` (变更后的键值对)。
  2. 匹配属性键是否属于 `custom-index-db-config` 中定义的继承列。
  3. 确认该块是否处于某个活动的数据库（AV）范围内。
  4. 如果匹配，立即计算受影响的后代范围，并触发属性向下传播。

### 5.2 核心挑战与应对 (Risk Management)
实现响应式同步必须解决以下“写放大”与“循环同步”问题：

1. **写放大与卡顿**：
   - **策略**：引入 **“防抖事务 (Debounced Transactions)”**。不要在父属性变更的瞬间处理成千上万的子块，而是将任务放入队列，利用思源的批量事务 API (`/api/transactions`) 进行一次性提交。
   
2. **循环依赖 (Circular Sync)**：
   - **风险**：方案 B 监听 `transactions`，其发出的更新操作又会产生新的 `transactions` 消息。
   - **策略**：**操作标记 (Operation Tagging)**。在发起 API 请求时，在 IAL 中带上一个临时的 `plugin-sync-timestamp` 或者是通过 Session ID 过滤。同步逻辑在收到消息时，如果检测到是由本插件触发的操作，则直接忽略。

3. **幂等性与历史记录控制**：
   - **策略**：强制执行 **“前置值对比”**。只有当计算出的继承值与子块当前 IAL 确实不一致时，才发起写操作。这能有效减少 `.sy` 文件的冗余变更和文档历史碎片的堆积。

### 5.3 结论：从“定时同步”向“增量触发”演进
虽然当前的“构建时同步”非常稳健，但**基于 WebSocket 的增量监听**是通往“极致自动化”的必经之路。

**演进建议**：
短期内保持当前的物化传递逻辑；中期可引入一个后台监听器，仅针对手动在数据库单元格内修改值的场景，进行小范围后代热更新，从而在不牺牲稳定性的前提下，实现属性的“准实时”继承。

## 6. 核心对决：动态计算 vs 物化同步 (Virtual vs Materialized)

在思源这种“以文件为底层、SQL 为索引”的架构中，选择哪种方案决定了插件的终极体验：

### 方案 1：动态计算 (Virtual Read-time)
数据库单元格留空，仅在展示或查询时向上追溯。
- **优点**：
  - **数据一致性完美**：父项一改，子项理论上瞬间“变”，不存在同步延迟。
  - **无写放大**：不产生冗余属性，不会导致 `.sy` 文件体积膨胀，不占用历史记录。
- **缺点**：
  - **搜索极难实现**：思源自带的搜索和 SQL 过滤无法搜到“继承的值”，因为数据库里它们是空的。
  - **跨平台瓶颈**：如果移动端或 Web 端没装插件/没运行逻辑，看到的仍是空值。
  - **计算开销**：每次渲染大表都要实时递归，性能随深度指数级下降。

### 方案 2：物化同步 (Materialized Change-time) - *当前采用*
变更发生时，将计算结果实时（或延时）写入子项的 IAL。
- **优点**：
  - **搜索性能极致**：标准 SQL、全局搜索、跨插件调用均可直接识别到继承后的值。
  - **自包含与解耦**：文档发给别人或在移动端看，属性都在，不依赖本插件实时运行。
  - **响应速度**：渲染时只是普通的属性读取，$O(1)$ 复杂度。
- **缺点**：
  - **写放大风险**：修改一个根节点属性，可能导致数千个子块同时更新 IAL。
  - **状态同步压力**：需要处理网络异常、插件崩溃导致的“部分更新”情况。

---

## 7. 终极推荐：物化同步 + 智能缓冲 (Materialized with Buffer)

**我们推荐并坚持方案 2（物化同步），但需要通过技术手段弥补其缺点：**

### 为什么方案 2 胜出？
对于“文档构建器”和“目录/大纲”场景，用户最核心的需求是 **“数据可被搜索”** 和 **“文档属性的确定性”**。如果继承的值搜不到，数据库的价值就减半了。

### 极致方案的进阶路线图：
1.  **静默写入 (Dirty Check)**：写入前必读，值没变绝不发起 API 调用（减少 80% 的写放大）。
2.  **异步缓冲队列 (Task Queue)**：当检测到大规模更新（如超过 50 个块）时，进入后台队列缓慢执行，并显示进度条，避免主界面卡死。
3.  **操作原子化 (Transactions)**：利用 `/api/transactions` 将多个子块的 IAL 变更合并在一个原子操作内提交，减少文件 IO 次数。
4.  **定期自愈 (Self-Healing)**：在文档打开时或构建器运行过程中，自动执行小规模的一致性校验，修复因意外中断导致的属性残缺。

**一句话总结**：方案 1 是技术人的完美理想，方案 2 是用户的生产力工具。我们选择 **方案 2**，并用“批量事务”与“脏检查”将其打磨至极致。
