# SOT (Single Source of Truth) 与数据绑定深度规划

在思源插件索引与属性继承功能的演进中，我们面临着核心数据归属权的挑战。目前，我们的系统中存在三种可能具备状态的实体：

1. **List (列表块)** : 用户最初输入文档大纲的地方。
2. **Page (文档/页面)** : Builder 基于列表生成的子文档。
3. **DB (数据库/Attribute View)** : 附着在列表或页面上，用于管理属性的视图。

为了确保这三者在各种组合下都能保持数据一致性且逻辑不至于过于复杂，我们需要明确谁是 **Single Source of Truth (唯一真实数据源, SOT)** 。

## 一、 现状分析与痛点

1. **组合复杂性**：用户的使用场景千变万化。

   - 场景 A：仅仅使用 List 生成了子 Page（无数据库）。
   - 场景 B：在 List 上建了 DB，但没有生成子 Page（纯属性管理）。
   - 场景 C：List 既生成了 Page，又绑了 DB（最复杂的完全体）。
2. **冗余的 Icon 列**：当前我们在 DB 中手动维护了一个 `Icon` 列以支持继承。其实思源的原生数据库（主键列）以及关联页面本身就有 Icon 属性，如果在主键/页面上修改，思源底层会自动级联。我们自己维护 Icon 导致逻辑重叠且容易冲突。
3. **反向同步冲突**：当非 SOT 的实体被用户手动修改时（例如：DB 是 SOT，但用户直接在 List 上手改了 Icon 或文本），插件该如何反应？

---

## 二、 核心决策提案

### 决策 1：消除多余的 Icon 继承列，转投思源原生

废弃自定义的 `Icon` 属性列继承。思源笔记已经内置了主键修改关联页面图标的功能。
**注：List 中提取 Icon 的要求**
当我们要把 List 作为源头（SOT）来拉取数据生成 Page 后，我们需要注意 List 中的表情支持范围：

- **只支持原生 Unicode Emoji**: 必须是诸如 `234asdg-eavnk-bbrmbroi` 这种系统原生或符合思源图床标准的标准形式。
- 如果遇到不支持的格式（或者是复杂的混合富文本格式），必须 Fallback 到一个“默认图标”。
- **改动计划**：移除 `syncInheritanceToDb` 中对所有关于 `Icon` 的特殊硬编码检索和覆盖，转而依靠建页（Builder）时的初次提取和后续单向绑定。

### 决策 2：SOT 的确立 (DB 绝对权威)

纠正这条最新的  **“权力链 / 优先级 (Hierarchy of Truth)”** ：

**SOT 优先级： DB (属性视图) > List (列表大纲) > Page (生成的页面)**

#### 为什么 DB 是绝对 SOT (Highest Priority)？

1. **批量管理优势**：DB 提供了宏观的表格视图，是集中批量管理、查阅所有条目结构化属性数据的天然最佳场所。
2. **数据沉淀**：属性（状态、数值等自定义 Meta）最稳定地储存在 DB 的单元格结构中，适合作为全局的最终参考标准。List 提供更优的富文本输入体验和层级关系，Page 作为最终阅读载体，但在核心数据指引上他们都要向 DB 看齐。

#### 场景详述与反向编辑策略：

 **【场景 A】：List + Page (无 DB)**

- **SOT**: **List (列表)** 。
- 策略：只要 List 不被折叠为单纯的引用块，那用户去单点某个子 Page 并修改了正文内容后，这部分内容可能无法自动反哺回 List（或者引发冲突）。为了确保相对核心地位，Builder 生成 Page 后，理应将 List 维持为内容的根基输入源，Page 作为其关联的视图。如果有修改，应该以 List 为准向下刷新 Page。

 **【场景 C】：List + Page + DB (完全体)**

- **SOT**: **DB (属性视图)** 。
- 策略：

  - 核心属性数据以 DB 为准。
  - 内容文本、图标：虽然 DB 是 SOT（特别是对图标来说，DB 主键会自动随 Page 变动），但是针对纯文本结构，List 依旧是最好的输入源。
  - 如果用户手动修改了 List（如改变了文本或符合规则的 Emoji 图标），那么 List 的改变应当被抓取并**单向流向 DB 和 Page**（例如更新关联页面的 Icon 和 DB 对应行的属性）。
  - SOT 的最高法则是：一旦发生冲突或需要全量同步，总是从 DB 取值（如果有）并向下游进行分发覆盖。
