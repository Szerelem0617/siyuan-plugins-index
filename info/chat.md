# 数据库属性继承：阶段性总结与后续展望

## 1. 现阶段工作总结 (已完成)

我们已经成功将属性继承方案从“虚拟动态解析”升级为 **“方案 2：物化同步 (Materialized Sync)”**。这是一个里程碑式的改进，标志着插件从单纯的文档生成器演变为具备数据管理能力的工具。

### 1.1 核心功能落地
- **物化写入**：现在修改继承规则后，插件会立即计算并将结果 **物理写入** 数据库单元格。这使得继承属性在思源原生搜索和 SQL 查询中完全可见。
- **双向一致性**：文档构建器 (Builder) 与 数据库设置 (Settings) 共享同一套逻辑。无论是通过 IAL 还是通过数据库界面，用户看到的数据都是一致的。
- **健壮的映射机制**：建立了 Block ID 与 Row ID 的可靠双向映射，解决了思源 API 在处理非第一列数据时的寻址难题。
- **可视化测试**：在设置界面集成了“继承测试”功能，支持一键打印全量解析结果，方便调试。

### 1.2 技术细节修复
- **ID 识别优化**：适配了思源单元格数据中复杂的 ID 结构（itemID vs blockID）。
- **Dirty Check (脏检查)**：实现了更新前的值对比，大幅减少了不必要的 API 调用。
- **UI 强制刷新**：通过更新数据库块时间戳，解决了 API 修改数据后前端界面不自动刷新的问题。
- **鲁棒性增强**：修复了多个作用域变量缺失（formatDate, isValueEmpty 等）和优化过早导致的逻辑漏洞。

---

## 2. 当前架构状态
- **存储模型**：物化存储（计算结果持久化于 .sy 文件）。
- **同步时机**：配置变更时全量同步 + 文档构建时增量覆盖。
- **性能等级**：中大型数据库（<1000行）表现良好；超大型数据库可能存在解析阻塞。

---

## 3. 接下来的工作 (Next Actions)

虽然核心方案已落地，但为了达到“极致高效”，后续工作将集中在性能优化和实时性上：

### 3.1 性能优化：批量事务提交 (Highest Priority)
- **现状**：目前每检测到一个变动就发起一次 API 请求。
- **改进**：收集所有 `updateOps`，通过单个 `/api/transactions` 任务一次性提交所有单元格变更。这将大幅减少网络开销和 SiYuan 的文件写入负担。

### 3.2 体验增强：异步同步与进度反馈
- **目标**：在执行全量同步时（如保存设置后），将同步过程移至后台任务，并为用户提供一个简单的进度提示，避免主界面在处理大型列表时出现短暂无响应。

### 3.3 响应式演进：WebSocket 监听 (Medium Term)
- **目标**：基于我们之前在 `chat.md` 中的调研，实现一个后台监听器。当用户在数据库中手动修改父项的某个值时，自动触发受影响子项的实时重算与物化同步。

### 3.4 逻辑完善：复杂类型支持
- **目标**：增强对 `mAsset` (资源)、`relation` (关联) 等复杂 AV 类型在 IAL 转换中的支持，确保非文本类型也能完美继承。

---

**总结**：我们已经跨过了“能不能用”的门槛，进入了“好不好用”和“稳不稳健”的精雕细琢阶段。当前的物化同步方案为用户提供了确定的、可搜索的数据价值。

## 4. 请教 SiYuan 核心源码专家的问题 (Supertag 功能开发)

专家你好，我们在开发“**超级标签 (Supertag)**”功能时遇到了关于 `ws-main` 事件和标签精准抓取的技术问题。
目前该功能的需求是：当用户在某个块中敲下一个形如 `#Type#` 的标签时，插件监听到这个动作立刻将此块自动添加到设定好的 AV 视图中。

目前的实现逻辑：
由于插件本身并没有 `this.eventBus` （我们之前误用了自己声明的局部 bus），现在已经成功将 Siyuan 全局的 `Plugin.eventBus` 传给了监听器，并监听了 `ws-main` 下的 `cmd === "transactions"`。在这些 actions (`update`, `insert` 等) 中，我们会获取到被修改块的 `id`，并通过 SQL 去查询它的 `ial` 提取 `tags="tag1 tag2"` 属性。然后对比是否命中了已注册的 Type 进而入库。

**当前面临的挑战：如何识别哪些是“刚刚打上的新标签”？**

当我们拦截到 `update` 事务或通过 SQL 拿到最新 `tags` 属性时，这个属性包含了该块上的所有历史标签和当前事务可能附加的新标签。这就导致如果用户修改了一个已经打好标签的块的内容，即使他没有动标签，我们拿到的 `tags` 也没有变化，但插件依然会遍历所有 tag 触发一次检查（虽然我们通过 `getAttributeViewItemIDsByBoundIDs` 做了防御从而不会重复入库，但会导致大量不必要的数据库查询和运算，不够优雅和高效）。

**问题核心：**
1. **如何从 `transactions` 数据结构本身，判断一个标签是刚“新增 (Added)”或“修改 (Modified)”的，而非一直存在于这个块上的？**
   在 `doOperations` 数组里的 `op.data` 到底包含什么样的 Diff 信息可以让我们快速得出结论？
2. 如果直接对比 `op.data` DOM 字符串或者 `op.ial`，思源是否提供了一种优雅的模型（Model）或辅助判定方法？
3. Siyuan 后端在处理标签索引时（例如往 SQLite 的 `tags` 表或 `blocks` 里的 `ial` 写入时），是否会单独广播类似 `tag-added` 或 `tag-updated` 的轻量事件供特定插件监听？还是必须在海量的 `transactions` 中硬解？

**【Update】目前的 Debug Plan**
为了弄清楚打标签（直接在块内输入 `#标签#` 时）底层真正的 payload 是什么样的，我已在 `supertag.ts` 中加入了一条极其底层的拦截日志。只要任何事务的数据（`op.data`）中包含 `"tag"` 或 `"#"` 这个字符，就会被打印出来：
`console.log("[Supertag] Inspecting potential tag op:", op.data)`

目前我知道属性界面设置的是 bookmark 而不是 tag，所以我们的目标是**完全拦截通过编辑器正文录入 `#XXX#` 的动作**。

## 5. 解决方案：检测“页面级别的 Tag (Page Tags)” (已完成)

感谢专家提供的线索。页面标签的更新确实不同于普通块：
- **动作类型**：使用的是 `updateAttrs` 而非 `update` 或 `setAttrs`。
- **数据结构**：Payload 是一个包含 `old` 和 `new` 属性的对象（或 JSON 字符串）。
- **分隔符**：页面标签在 IAL 中是以英文逗号 `,` 分隔的。

**已实施的改进：**
- 更新了 `supertag.ts` 中的 `handleWsMessage` 以监听 `updateAttrs` 动作。
- 增强了 `extractTagsFromPayload` 方法，使其能识别 `data.new.tags` 结构，并自动根据内容选择逗号或空格作为分隔符。
- 现在给页面（文档）添加标签也能像普通块一样触发超级标签自动分类逻辑。
