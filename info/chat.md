# 思源 Issue 提交草稿

## 问题描述
在编辑器中使用 `Shift+Tab` 提升列表项层级时，若该列表项已绑定到属性视图（数据库），其在数据库中的行级数据会瞬间消失。

## 预期结果
提升列表项层级仅改变其在文档树中的位置，不应触发属性视图（数据库）中关联行数据的删除。

## 更多信息（内核追踪分析）
经过对思源核心源码的初步追踪，该问题疑似源于 **后端 AST Diff 的遍历逻辑缺陷**：

1. **操作行为**：前端提升层级时通过 DOM 移动块，并移除因变为空白而多余的旧 `NodeList` 容器。随后发送 `updateTransaction`。
2. **内核逻辑漏洞点**：`kernel/model/transaction.go` 中的 `doUpdate` 函数通过 `getRemovedNodes` 识别出旧的空 `NodeList` 已被删除。
3. **连锁反应**：程序对该“被删除”的 `NodeList` 调用了 `syncDelete2AvBlock` -> `syncDelete2AttributeView` 进行数据库关联清理。
4. **致命错误**：在 `syncDelete2AttributeView` 内部使用 `ast.Walk` 遍历**旧内存树中的节点**。此时旧树中被标记删除的 `NodeList` 指针下方依然悬挂着其子项（即那个被移动走的块）的 AST 节点。
5. **结论**：内核错误地认为这些子项也随容器一同物理删除了，从而向数据库发出了 `RemoveBlockRel` 指令，导致数据库行数据被硬删除。

**建议修复方向**：在物理删除数据库关联前，校验子项 ID 是否已在本次事务的新树 (`updatedNode`) 中作为 Move 后的新位置出现。
