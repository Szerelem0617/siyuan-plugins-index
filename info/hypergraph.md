## 5. 终极形态：无状态（Stateless）与纯属性视图（AV）架构

为了实现数据的终极掌控感，超图的存储应遵循“插件不存业务数据，数据全在用户文档”的原则。即使插件停用，数据依然清晰可读。我们将**完全基于思源原生的属性视图（Attribute View）**来实现这一目标。

### 5.1 数据映射：如何用 AV 表达超图？

在 `list/action.ts` 中，我们已经实现了将列表项转化为“节点（Entities）”并存入 AV 的能力（自动生成 Level, Father, Path 等结构字段）。那么，多对多的“超边（Hyperedges）”该如何存储？

答案是：**超边本身也是一个独立的属性视图（AV），利用“关联（Relation）”字段连接作为节点的 AV。**

#### 需要几个 AV 表？分别是什么？

通常我们需要构建 **1 + N** 的架构矩阵：

1. **节点池视图 (Node Pool AV)** —— `1` 个（或根据大类拆分少数几个）
   - **作用**：存储实际的知识对象/碎片实体（概念、人物、任务、引言等）。
   - **特点**：这就是我们目前通过插件列表生成器 `createDatabaseWithBlocks` 建立的视图。
2. **超边关系视图 (Hyperedge Type AVs)** —— `N` 个
   - **作用**：每定义一种“超边（系统/框架）类型”，就对应建立一个独立的数据库。
   - **示例**：例如创建一个 `[超边] 物理公式库`、一个 `[超边] 会议记录库`、或一个 `[超边] 逻辑推导关系库`。

### 5.2 超边视图 (Hyperedge AV) 的具体结构与必备字段

以一个名为 `[超边] 逻辑推导` 的 AV 为例，它作为连接多个实体的超边，在思源中必须包含以下具体列和必备字段：

| 列名 / 含义 | 类型 (KeyType) | 具体形式与数据来源 | 插件核心作用 |
| :--- | :--- | :--- | :--- |
| **主键 (Instance ID)** | 块 (Block) | 代表这个“超边关系”本身的标识。通常由插件后台调用 `insertBlock` 生成一个无文本的幽灵块（或用户手写的关系总结语）放入 AV 中作为主键。 | 唯一标识该次超边连接。 |
| **超边名称 (Name)** | 文本 (Text) | 用户对这个关系的命名，例如“苏格拉底的三段论”。 | 可选，增强人类阅读数据的体验。 |
| **角色 A (Role A)** | **关联 (Relation)** | **核心必备字段**。比如命名为 `前提1` 列。它是一个双向或单向关联字段，其值是指向**节点池 AV** 中的某个或某几个实体的块 ID。 | 插件负责自动解析并填入 ID，完成连线。 |
| **角色 B (Role B)** | **关联 (Relation)** | **核心必备字段**。比如命名为 `结论` 列。同上，指向另一个（些）节点块。 | 插件负责建立节点间的空间拓扑约束。 |
| **权重/属性 (Props)**| 数字/单选/日期 | 描述这个超边环境的元数据。比如这条逻辑推导的 `置信度(Number)` 或 `提出时间(Date)`。 | 提供额外的高级图查询或过滤维度。 |

### 5.3 插件的职责引擎：化身“AR 眼镜”

既然数据全部规规矩矩地躺在 AV 表格（ JSON）中，插件将完全抛弃自己维护一套关系库的包袱。插件的运作方式将变成这样：

1. **反向查询引擎 (Reverse Lookup)**：
   当用户光标悬停在某个“节点池”的块上时，插件通过截获它的 Block ID，去查询**所有超边视图中，Relation 关联字段包含了当前块 ID 的行**。从而在边缘侧边栏直接展示出：“这个概念块，目前参与了 3 个推导进程和 1 个会议探讨”。
2. **快捷生成连线 UI (Quick Entry)**：
   超图编辑是很麻烦的，我们不需要用户去面对庞大的表格填空。借助插件介入：用户只需在编辑器高亮选中几个知识块，按下快捷键（例如 `Ctrl+Shift+E`），弹出一个“关系打结器”UI。用户选择超边类型为 `逻辑推导`，将选中的块拖入 `前提` 和 `结论` 槽位（Slot）。
   点击确认后，**插件自动在对应的超边 AV 中新建一行（创建主键块），并通过 API 自动填充对应的 Relation 关联字段**。
3. **全局渲染器 (Global Canvas)**：
   当用户需要大局观时，插件只需遍历提取那 `N` 个超边 AV 表格里的 Relation 关系数据流，解析出所有的 Node 和 Edge，立刻就能在白板或浮窗中还原出 N 元超图的视觉拓扑，喂给图形库（如 G6 / ECharts）进行终极宣发渲染。

### 5.4 总结

通过这种 `1+N` 的纯 AV 表格架构（节点表 + N个类型的超边表），我们达到了最优雅的境界：
- 抛弃了利用不可见的 IAL (`custom-`) 暗改属性可能带来的混乱和数据孤岛。
- 最大限度、最正确地使用了思源自带的核心利器：**Relation (关联)** 列类型。
- 保证了数据架构的**绝对抗脆弱性**：无论未来插件形态发生什么变更，用户甚至直接卸载插件，他们辛苦建立的知识脉络也毫不受损——因为打开表格本身，就是一组组完美关联的思源原生数据库列表。这就是本地优先（Local-first）插件开发的究极浪漫。

## 6. 后续研发路线图 (Roadmap)

针对这种 `1+N` 架构，我们的思源插件在接下来的开发中可以分为三个阶段来逐步实现：

### 阶段一：极速查询与上下文展示 (Context Pane)
**目标：让用户看到块周围隐藏的超边关系。**
1. **获取所有的超边（Hyperedges）**：
    - 在插件中建立一个特殊的“配置块”，记录所有作为 Hyperedge 系统的 AV-ID 集合。
2. **实现反向查询函数**：`getAvRelationsByBlockId(blockId)`
    - 当用户焦点移动到一个普通的实体块（Node）时，插件在后台发送请求遍历上述集合中的 AV。
    - 检查 AV 中的 `Relation` 列，看 `blockIds` 数组中是否包含当前 `blockId`。
3. **构建侧边栏/悬浮窗界面 (UI)**：
    - 如果该实体属于某个超边，就在右侧面板渲染：“关联于 [物理公式:牛顿第二定律]，取决于 [质量 (块ID)]”。

### 阶段二：建立“关系打结器” (Quick Relator UI)
**目标：极大降低用户在 AV 表格间连线的心智负担。**
1. **多选探测**：监测用户的选中操作，如果选中了不同文档里的 1-3 个块，呼出一个悬浮按钮。
2. **打结器表单 (Relator Dialog)**：
    - 面板提供下拉菜单让用户选择“超边架构”（比如选择了“逻辑推导网”对应的 AV）。
    - 自动拉取该 AV 中所有类型为 `Relation` 的列，作为不同的“插槽（Slots）”（如 `前提`、`结论`）。
    - 允许用户将刚刚选中的被高亮的块拖拽，或者点选填入对应的插槽中。
3. **自动化 API 调用**：
    - 点击“打结”（Connect），插件静默调用 `/api/av/addAttributeViewBlocks` 往那个“超边 AV”插入新行作为主键。
    - 紧接着用 `batchSetAttributeViewBlockAttrs`，把上面步骤确定的目标块 IDs 写入这一行的各个 `Relation` 单元格中。
    - 关系构建完成，全程无需用户面对庞大的数据表。

### 阶段三：超图全景渲染 (Global Graph Lens)
**目标：从数据的底层飞跃到高维可视化。**
1. **数据集装配提取 (Data Assembly)**：
    - `Nodes` Array：拉取用户作为碎片的 Node Pool AV，提取 id, name。
    - `Edges` Array：拉取上述 Hyperedge AV，把含有多个 `Relation` ID 的每一行，根据用户对这个关系的定义结构化为超级边。
2. **适配多维可视化图表 (ECharts/G6/React Flow)**：
    - 因为这些图表库本质上也只是一堆 Node 和 Edge 对象数组，我们要做的只是映射。
    - 引入过滤面板，允许用户通过各种属性标签，在高阶图形化层级上过滤知识，比如“只看属于 2024 年 Q1 并且由超边类型 [竞品分析] 所关联构建出的局部子图”。

## 7. 架构深究：3表理论 vs 1+N 属性视图模型

在标准的图数据库理论或 SQL 架构设计中，表达 Hypergraph（如 `F=ma` 或“精灵种族羁绊”）通常需要标准的 **3列表理论**：
1. **Node Table (节点表)**：存实体（F, m, a）。
2. **Hyperedge Table (超边表)**：存关系本体（牛顿第二定律 E01）。
3. **Incidence Table (映射表)**：存节点和超边的多对多连接状态及槽位（`F`->`E01` as 左值）。

### 关系物化 (Relationship Reification)
这也是图数据库应对复杂关系的终极解法：**把“关系（行为）”当作“实体（名词）”来处理。**
在传统图中，一条边只是 `A -> B`。在物化超图中，关系变成了一个中心实体 `Relation_Node`，A 和 B 都作为参与者（拥有各自的 Role）指向这个事件中心。

### 为什么我们选择 1+N (AV模型) 而不是原生 3表？

我们用思源的 **（1 个 Node AV + N 个 Hyperedge AV）** 架构，本质上就是对 **3表理论 / 关系物化** 的一次降维变种。但结合思源的实际限制，1+N 是更佳设计：

| 维度 | 标准 SQL 3表模型 | 我们的 1+N AV 架构 | 优劣势解析 |
| :--- | :--- | :--- | :--- |
| **超边主体存储** | Hyperedge Table | **Hyperedge AV (一个特定的表格)** | **等效**。在我们的架构中，N 的存在就是将“事件/关系”物化为了实体表。 |
| **映射关系存储** | Incidence Table 里的 Role 字段 | **Hyperedge AV 中的 Relation 类型的列 (Column)** | **AV 的核心优势**。思源的 Relation 列本身就自带了包含（数组）能力。一个列代表一个 Role（如`左值`），列内的单元格就是 `[A, B...]` 的外键数组。我们不需要第三张物理映射表，这是针对 JSON 文档型数据库最完美的剪裁。 |
| **用户可读性** | 极低（全是枯燥的映射 ID） | **极高**（每一段超边关系就是表格里清晰的一行） | **AV 的绝对碾压**。用户可以在无需插件介入的情况下，直接用思源自带的 UI 阅读和编辑超边关系。 |
| **异构数据处理** | 所有超边混塞在一个表，靠 `type` 区分，查询极其臃肿。 | **分表存储 (N)**。`逻辑推导AV` 和 `游戏羁绊AV` 是分开的表格。 | **AV架构更优**。你可以给每一类超边单独设定特有的 Props 列（推导有置信度，羁绊有增益数值）。互不干扰。 |

### 7.1 进阶拷问：如果 Schema 爆炸怎么办？（严格 3-AV 表模型）

这就是你刚才提出的非常致命且深刻的架构拷问：**如果一个高中知识树里有 80 个不同的物理公式，难道我们要建 80 个 AV 表吗？**

如果采用 `1+N` 模型，确实会面临这种 **Schema 爆炸（模式激增）** 的问题。因为每个公式的变量数量和名称（Role 名）都不一样（比如 `F=ma` 有 3 个变量，万有引力公式有 5 个变量），强行塞进一个表会导致大量空列，或者退化成通用列名（`变量1`, `变量2`），丧失语义。

在这种极端复杂的终极场景下，你提到的**“直接在思源里用 3 个 AV 表完美复刻底层关系库”**就成了必须的王牌方案。这就是 **“无模式字典图结构 (Schema-less Dictionary Graph)”**。

#### 终极 3-AV 架构设计（应对万物互联）

我们完全可以只建 3 个固定的 Attribute View：

1. **`AV1: 节点大纲 (Nodes)`**
    - **主键**: 节点自身（F，m，a，速度，牛顿）。
    - **属性**: 类型（如：物理量、人物）。

2. **`AV2: 超边大纲 (Hyperedges)`**
    - **主键**: 关系本体（牛顿第二定律，万有引力定律，游戏羁绊 A）。
    - **属性**: 类型（如：物理公式，剧情冲突）。

3. **`AV3: 角色映射表 (Incidence / Mappings)`** —— **这是超图的灵魂**
    - **主键**: 自动生成的幽灵块（代表一次角色扮演）。
    - **列 A (Relation)**: 指向 `AV2 (超边表)`（例如指向了“牛顿第二定律”）。
    - **列 B (Relation)**: 指向 `AV1 (节点表)`（例如指向了“质量 m”）。
    - **列 C (Select / Text)**: **角色 (Role) 枚举**（填写“乘数”或“前提条件”）。

#### 这种严格 3-AV 方案的优劣探讨：

- **无敌的扩展性**：不管你有 80 个物理公式，还是 800 个法律条文，AV 表永远只有这 3 个。表结构永不膨胀！数据就像字典一样整齐排列在 `AV3` 这个中间表里。在底层处理上远比 1+N 方案通用。
- **可怕的用户体验灾难**：你必须接受一个事实，`AV3 (映射表)` 对碳基生物是完全不可读的。它是一长串的 `[牛顿第二定律] - [质量m] - [乘数]`、`[牛顿第二定律] - [加速度a] - [乘数]`。你绝对不想直接去填这个表格。

#### 破局之道：插件统管 `AV3`
如果你选择这套完美的 3-AV 表架构，你的插件就必须 100% 承担起 UI 渲染和数据组装的责任。
用户在前端完全看不到 `AV3`，他们只通过插件提供的**“公式编辑器连线”**或**“思维导图白板”**进行交互，插件在后台默默地转化为成百上千条插入 `AV3` 中间表的请求。

**总结如何选：**
- **业务场景稳定、分类扁平**（比如 GTD 任务管理带子任务，或是固定流程的写作看板）：使用 **1+N 表格**，因为用户经常需要打开特定类型的表格进行批量浏览和手动拉拽。
- **知识网极其庞杂、动态 Role、极度抽象**（比如多学科融合知识库、物理公式全集）：毫不犹豫地上 **3表格（节点、超边、映射）大一统模型**，然后用插件写一个无敌的图形化前端来彻底屏蔽后端的复杂映射表。这是大型知识图谱的最佳流派。
