# 群 (Cluster) 概念设计与架构分析

> "A cluster of concepts that are tightly related"
> 群是基于 Hypergraph 思想，将一组紧密相关的概念圈在一起，突破图数据库 1:1 关系限制的高阶关系管理方式。

---

## 一、群的本质：从图论到知识管理

### 1.1 为什么需要群？

传统的笔记关系工具只能表达 **1:1** 的二元关系：
```
A → B      （块引用：A 引用了 B）
A ← B      （反链：B 引用了 A）
A ↔ B      （双向链接）
```

但现实中的知识关系大量是 **N:N** 的：
```
I = Anvq   → {I, A, n, v, q} 五个物理量构成一个不可拆分的关系群
刺客羁绊    → {卡特, 劫, 阿卡丽, 派克} 四个角色共享"刺客"身份
苏格拉底三段论 → {大前提, 小前提, 结论} 三个命题构成一个逻辑群
```

**群**就是这些 N:N 关系的第一等公民表达。它不是"多个 1:1 关系的集合"，而是一个**原子性的整体**。

### 1.2 群 vs 超边 vs 标签

| 概念 | 你已有的实现 | 群的区别 |
|:---|:---|:---|
| **标签 (Tag)** | `#Physics` 标记一个块属于物理领域 | 标签是**分类标注**，没有成员间的关系语义 |
| **超边 (Hyperedge)** | hypergraph.md 中的 1+N/3-AV 模型 | 超边强调**带角色的连接**（如 F=ma 中 F 是"结果"，m 是"乘数"） |
| **群 (Cluster)** | 🆕 本文设计 | 群强调**成员身份与聚合**。成员地位对等，共享群属性，可被统计 |

**关键区分**：超边是"关系物化"——把一个关系变成实体；群是"集合物化"——把一个集合变成实体。两者互补而非替代。

## 二、群的两种生成方式

### 2.1 纵向群：从列表层级自动生成

当用户创建一个知识树列表并将其加入数据库时，层级结构天然产生嵌套的群关系：

```
📖 高中物理 (topic)                      ← 大群 G1: 所有物理知识点
├── ⚡ 电学 (segment)                    ← 中群 G2: 所有电学知识点
│   ├── 欧姆定律 (keypoint)              ← 小群 G3: 电学·基础定律
│   ├── 基尔霍夫定律 (keypoint)
│   └── 电功率公式 (keypoint)
└── 🔧 力学 (segment)                   ← 中群 G4: 所有力学知识点
    ├── 牛顿第二定律 (keypoint)           ← 小群 G5: 力学·牛顿定律
    └── 万有引力定律 (keypoint)
```

**自动推导的群成员关系**：

| 群 | 成员 | 生成规则 |
|:---|:---|:---|
| G1 (高中物理) | 欧姆定律, 基尔霍夫, 电功率, 牛二, 万有引力 | root 下所有 leaf 节点 |
| G2 (电学) | 欧姆定律, 基尔霍夫, 电功率 | 该 segment 下所有 leaf |
| G4 (力学) | 牛二, 万有引力 | 该 segment 下所有 leaf |

**技术实现**：利用已有的列表生成器（`list/action.ts`）中的 Level/Father/Path 字段，在块被加入 AV 时自动计算其所属的纵向群。这些群关系存储在 SQLite 或 AV 的计算列中。

### 2.2 横向群：用户手动归纳

用户自己发现的跨层级、跨领域关联：

```
群「电流公式 I=Anvq」
  成员：[I (电流), A (横截面积), n (载流子浓度), v (定向速度), q (电荷量)]

群「力学-电学桥梁」
  成员：[牛二定律, 洛伦兹力, 电场力]
  描述：这三个定律构成了从力学到电磁学的核心过渡

群「考试高频考点」
  成员：[欧姆定律, 牛二定律, 万有引力, 电功率公式]
  描述：近五年高考出现频率 > 80%
```

**关键问题**：横向群不存在天然的层级结构，需要用户显式创建。

## 三、主键设计：核心技术决策

### 3.1 三种候选方案

#### 方案 A：成员之一作为主键（Member-as-PK）

```
AV: 群数据库
┌──────────────────┬───────────┬────────────────────────────┐
│ 主键 (Block)     │ 群名      │ Members (Relation)          │
├──────────────────┼───────────┼────────────────────────────┤
│ [I (电流)]       │ 电流公式   │ [A, n, v, q]              │
│ [欧姆定律]       │ 基础定律群 │ [基尔霍夫, 电功率公式]      │
└──────────────────┴───────────┴────────────────────────────┘
```

**❌ 致命缺陷**：
- I 做了"电流公式"群的主键后，不能再做"常见电学量"群的主键
- Members 列不含主键本身，需要额外逻辑"主键也是成员"
- 语义上不对等：主键有特殊地位，但群成员应该是平等的

#### 方案 B：Detached 独立实体作为主键（Cluster-as-Entity）⭐ 推荐

```
AV: 群数据库
┌──────────────────────┬───────────┬────────────────────────────────┐
│ 主键 (Block)         │ 群名      │ Members (Relation)              │
├──────────────────────┼───────────┼────────────────────────────────┤
│ [📎 群实体-001]      │ 电流公式   │ [I, A, n, v, q]               │
│ [📎 群实体-002]      │ 基础定律群 │ [欧姆, 基尔霍夫, 电功率]       │
│ [📎 群实体-003]      │ 常见电学量 │ [I, U, R, P]                  │  ← I 可以自由出现
└──────────────────────┴───────────┴────────────────────────────────┘
```

**✅ 优势**：
- 任何块可以出现在无限多个群的 Members 中
- 群本身是一个独立的块（可以被引用、被标记、出现在文档中）
- 群成员完全对等，没有"群主"概念
- 可以在群实体块中写入群的描述和上下文
- 和 hypergraph.md 中的"超边主键 = 独立块"思路一致

**⚠️ 取舍**：需要创建"幽灵块"或专门的群描述段落作为主键

#### 方案 C：混合方案（主键+扩展 Members）

```
主键本身也是成员，但 Members 列额外包含主键 → 数据冗余但语义清晰
```

**❌ 不推荐**：数据冗余带来一致性维护负担。

### 3.2 推荐结论

**使用方案 B（Detached 独立实体）**。群实体块可以是：
- 一个带文字描述的段落（如"电流公式 I=Anvq 描述了..."）
- 一个纯标记块（由插件自动生成的最小块）
- 甚至是一个文档块（一整篇文档代表一个群）

## 四、群的属性继承模型

### 4.1 核心问题：群属性 vs 成员属性

当一个块加入群之后，它应该获得什么？

#### 层次 1：群标识属性（自动获得）

```
块 [欧姆定律] 加入 群「基础定律群」
  → 欧姆定律自动获得：
    - custom-clusters: ["群实体-002"]     ← 记录所属群 ID
    - 或通过 AV Relation 反查获得群信息
```

#### 层次 2：群共享属性（继承）

```
群「考试高频考点」有属性 { 重要等级: "S", 复习频率: "每周" }
  → 所有成员是否自动获得 重要等级=S？
```

**设计建议**：**不做隐式继承，改为查询时聚合**。

理由：
- 如果隐式继承，成员加入/退出群时需要大量的属性同步操作
- 成员可能属于多个群，属性冲突难以解决（群A说重要等级S，群B说重要等级A）
- 更好的方式是：查询时动态计算"这个块通过群关系继承了什么属性"

```typescript
// 伪代码：动态聚合群属性
function getEffectiveAttributes(blockId: string) {
    const ownAttrs = getBlockAttributes(blockId);          // 块自身属性
    const clusters = getClustersOfBlock(blockId);           // 所属群列表
    const inheritedAttrs = clusters.flatMap(c => c.attrs);  // 群属性展开
    return mergeAttributes(ownAttrs, inheritedAttrs);       // 合并（自身优先）
}
```

#### 层次 3：群触发的身份获得（你的核心洞察）

> "tag 一个块 → 这个块获得属性加入数据库 → 其它这个数据库中的 block 会自动获得属性 → 由于拥有类相关属性 → 自动为 xx 类"

这里描述的是一个**传染性的类身份获得**机制：

```
步骤：
1. 用户给块 A 打上 #Cluster:电流公式
2. 块 A 被加入「群数据库」AV
3. 群数据库中已有成员 [I, A, n, v, q]
4. 这些成员因为身处同一个数据库 → 自动获得某种共享身份
5. 这种共享身份触发 L3 的类系统 → 成员自动获得特定的命令和行为
```

**关键设计**：身份判定标准应该是**数据库归属 + 列值**，而不是标签。

## 五、从 Tag 检测到数据库驱动的身份系统

### 5.1 你的洞察总结

> "不该以 tag 检测作为类检测标准，而是应该以数据库配置和关联属性来作为唯一标准"

这是一个架构范式转移：

| 维度 | 旧模式（Tag-driven） | 新模式（DB-driven） |
|:---|:---|:---|
| **身份来源** | 块上有 `#Project` 标签 | 块存在于 Project-DB 的 AV 中 |
| **身份判定** | `block.tags.includes("Project")` | `AV.hasBlock(blockId)` |
| **多身份** | 多个标签 | 出现在多个 AV 中 |
| **细分身份** | 需要 `#Project-Active`, `#Project-Done` 等子标签 | AV 中的"状态"列值 |
| **行为绑定** | L3 检查标签 → 挂命令 | L3 检查 AV 归属 + 列值 → 挂命令 |
| **属性管理** | 需要额外的 custom- 属性 | AV 列即属性 |

### 5.2 层级职责重新划分

```
┌─────────────────────────────────────────────────────┐
│  Layer 3: 类注册表 (行为管理)                         │
│  "这个类能做什么" → 右键菜单 / 按钮 / 生命周期         │
│                                                     │
│  身份判定：块属于哪个 AV + 列值是什么                    │
│  Tag 角色：只是入口（触发加入 AV），不是身份标准         │
│                                                     │
│  新增：方法权限管理（按角色列值区分可用命令）             │
├─────────────────────────────────────────────────────┤
│  Layer 4: 数据库配置 (属性管理)                        │
│  "这个数据库的列怎么配" → 列映射 / 值继承              │
│                                                     │
│  Tag 角色：触发"加入 AV 数据库"操作                    │
│  属性获得：加入 AV 后自动获得列定义的属性                │
│                                                     │
│  新增：View 管理（不同身份看到不同的列）                 │
└─────────────────────────────────────────────────────┘
```

### 5.3 纵向身份管理：用列区分角色

在同一个 AV（群数据库）中，不同的成员可以有不同的"角色"，通过**列值**区分：

```
AV: 物理知识群
┌──────────────┬──────────┬──────────┬───────────────────────┐
│ 主键 (Block) │ 角色     │ Level    │ 所属群 (Relation)      │
├──────────────┼──────────┼──────────┼───────────────────────┤
│ [高中物理]   │ topic    │ 1        │ -                     │
│ [电学]       │ segment  │ 2        │ [群:高中物理]          │
│ [欧姆定律]   │ keypoint │ 3        │ [群:电学, 群:基础定律]  │
│ [电流公式群] │ cluster  │ -        │ -                     │
└──────────────┴──────────┴──────────┴───────────────────────┘

角色 → View 映射：
  topic    → 看到：子章节数、知识点总数、掌握进度
  segment  → 看到：知识点列表、练习题数
  keypoint → 看到：公式、关联知识点、错题数
  cluster  → 看到：成员列表、群描述、聚合统计
```

不同角色看到不同的 View 列，这解决了"一个 group 里所有属性被限制为全同"的问题。思源 AV 的 View 功能天然支持不同的列显隐和排序/过滤配置。

### 5.4 方法权限管理

**问题**：属性可以用 View 控制可见性，但**方法/命令**怎么根据身份做权限管理？

**方案：在 L3 类注册表中引入 Role 条件**

```
L3 类定义（新版）：

Class Name: PhysicsKnowledge
Identity Source: AV "物理知识群"          ← 身份来源是 AV，不是 Tag
Role Column: "角色"                       ← 用哪个列区分角色

Role-Based Commands:
  topic:
    ContextMenu: [展开知识树, 生成大纲, 统计覆盖率]
    Button: [快速添加子章节]
  segment:
    ContextMenu: [展开知识点, 添加练习题]
    Button: [标记已学]
  keypoint:
    ContextMenu: [查看关联公式, 查看所属群, 添加到群]
    Button: [标记掌握, 添加闪卡]
  cluster:
    ContextMenu: [展开群成员, 聚合统计, 编辑群]
    Button: [添加成员, 移除成员]
```

**运行时解析**：
```
1. 用户右键一个块
2. 检查该块属于哪些 AV → 找到 "物理知识群" AV
3. 查 L3 → Identity Source 匹配 → 找到 PhysicsKnowledge 类
4. 读取该块在 AV 中的 "角色" 列值 → "keypoint"
5. 查 Role-Based Commands → 加载 keypoint 对应的右键菜单
6. 渲染：[查看关联公式, 查看所属群, 添加到群]
```

## 六、群的存储架构

### 6.1 方案选型

结合 hypergraph.md 中的分析和群的特点，推荐以下组合方案：

#### 轻量级群（推荐 MVP）：单 AV + Members Relation

```
AV: 群注册表 (Cluster Registry)
┌──────────────────┬─────────┬──────────┬──────────────────────┬──────────────┐
│ 主键 (Block)     │ 群名    │ 群类型   │ Members (Relation)    │ 描述         │
├──────────────────┼─────────┼──────────┼──────────────────────┼──────────────┤
│ [📎 C-001]       │ 电流公式 │ 公式群   │ [I, A, n, v, q]      │ I=Anvq      │
│ [📎 C-002]       │ 基础定律 │ 知识群   │ [欧姆, 基尔霍夫]      │ 电学基础     │
│ [📎 C-003]       │ 刺客羁绊 │ 游戏群   │ [卡特, 劫, 阿卡丽]    │ 收集3/6加成  │
└──────────────────┴─────────┴──────────┴──────────────────────┴──────────────┘
```

**优势**：简单、一张表搞定、AV 的 Relation 列天然支持多对多
**限制**：所有群共享同一套附加列（群类型相关的特殊属性无法差异化）

#### 重量级群（Phase 2）：群注册 + 节点池 + 映射表

如果群的语义更复杂（成员在群中有不同角色、不同权重），退化到 3-AV 模型：

```
AV1: 节点池（所有知识点）
AV2: 群注册表（群实体 + 群属性）
AV3: 成员映射表 → 群实体 (Relation to AV2) + 成员 (Relation to AV1) + 角色/权重
```

### 6.2 SQLite 辅助层

AV 存储群的定义和成员关系（用户可见、可编辑、抗脆弱），SQLite 存储**高频查询的反向索引**：

```sql
-- SQLite: 群成员反向索引（加速"这个块属于哪些群"的查询）
CREATE TABLE cluster_membership (
    block_id TEXT NOT NULL,
    cluster_id TEXT NOT NULL,
    cluster_av_id TEXT NOT NULL,
    cluster_name TEXT,
    updated_at INTEGER,
    PRIMARY KEY (block_id, cluster_id)
);

-- 查询：块 X 属于哪些群？
SELECT cluster_name FROM cluster_membership WHERE block_id = 'block-xxx';

-- 查询：群 Y 有多少成员？
SELECT count(*) FROM cluster_membership WHERE cluster_id = 'cluster-yyy';
```

**同步时机**：AV 数据变更时（通过 ws-main 事件捕获），增量更新 SQLite 反向索引。

## 七、群的交互设计

### 7.1 创建群

**纵向群（自动）**：
```
用户创建列表 → 加入 AV →
插件检测层级结构 → 自动生成群实体 → 填充 Members Relation
```

**横向群（手动）**：
```
方式 1: 多选块 → 右键 "创建群" → 弹出群编辑器
方式 2: 在群注册表 AV 中手动新增一行 → 拖入成员
方式 3: Slash 命令 /createCluster → 依次选择成员
```

### 7.2 查看群关系

**在块上查看**（反向查询）：
```
┌─────────────────────────────────────────┐
│  📌 欧姆定律                             │
│                                         │
│  所属群：                                │
│  ├── 📦 基础定律群 (3 members)           │
│  │   └── 欧姆定律, 基尔霍夫, 电功率      │
│  ├── 📦 电学 (5 members)                │
│  │   └── 欧姆, 基尔霍夫, 电功率, ...     │
│  └── 📦 高考高频考点 (4 members)         │
│      └── 欧姆, 牛二, 万有引力, 电功率     │
│                                         │
│  [展开全部] [添加到新群]                  │
└─────────────────────────────────────────┘
```

**实现方式**：悬浮面板 / 侧边栏 / 右键菜单子菜单

### 7.3 聚合统计

群的核心价值之一是**对成员的聚合操作**：

```
群「刺客羁绊」统计：
  ├── 成员总数：6
  ├── 已收集：3 (卡特✅, 劫✅, 阿卡丽✅)
  ├── 未收集：3 (派克❌, 千珏❌, 泰隆❌)
  ├── 收集率：50%
  └── 羁绊效果：3刺客 → 全体暴击率+15%

群「高考高频考点」统计：
  ├── 成员总数：4
  ├── 已掌握：2 (欧姆✅, 牛二✅)
  ├── 复习状态：1 待复习, 1 未开始
  └── 预计分值覆盖：40分
```

**技术实现**：
- 聚合规则可以配置在"群类型"上
- 对于简单的 count/sum，直接 SQL 计算
- 对于复杂的"羁绊效果"，用 L2 命令变体 + Param 配置规则

## 八、与自走棋/羁绊系统的融合

你提到的"云顶之弈"式羁绊是群概念的**游戏化完美案例**：

### 8.1 羁绊 = 群 + 阈值触发

```
群定义：
  群名: 刺客羁绊
  群类型: 羁绊 (Synergy)
  成员: [卡特, 劫, 阿卡丽, 派克, 千珏, 泰隆]
  阈值效果:
    2 → 全体暴击率 +10%
    4 → 全体暴击率 +25%, 暴击伤害 +20%
    6 → 全体暴击率 +40%, 暴击伤害 +50%, 技能冷却 -20%
```

**与 ECS 的结合**：
```
Entity: 卡特 (棋子块)
Components: #Chess, #Assassin, #Mage
  → 属于群 "刺客羁绊" + 群 "法师羁绊"

System:
  当用户在棋盘文档中放置棋子块（块引用嵌入）时：
  → 扫描棋盘中所有棋子的群归属
  → 计算每个群的激活成员数
  → 达到阈值 → 触发效果（修改属性 / 显示特效）
```

## 九、架构整合：群如何融入四层架构

### 9.1 群在各层的位置

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: 命令注册表                                  │
│  新增命令：                                           │
│    - cluster.create (创建群)                          │
│    - cluster.addMember (添加群成员)                    │
│    - cluster.removeMember (移除群成员)                 │
│    - cluster.aggregate (聚合统计)                      │
│    - cluster.query (反向查询所属群)                     │
├─────────────────────────────────────────────────────┤
│  Layer 2: 命令工厂                                    │
│  新增命令变体：                                        │
│    - "创建刺客羁绊群" (cluster.create, {type:"synergy"}) │
│    - "查看知识群关系" (cluster.query, {view:"panel"})    │
│    - "群统计-学习进度" (cluster.aggregate, {metric:"mastery"})│
├─────────────────────────────────────────────────────┤
│  Layer 3: 类注册表  (DB-driven Identity)              │
│  新增类：                                             │
│    - ClusterEntity:                                   │
│        Identity Source: 群注册表 AV                    │
│        Role Column: 角色                              │
│        cluster角色: [展开成员, 聚合统计, 编辑群]         │
│        member角色: [查看所属群, 退出群]                  │
├─────────────────────────────────────────────────────┤
│  Layer 4: 数据库配置                                   │
│  群注册表 AV 的列配置：                                 │
│    - 群名 (Text)                                      │
│    - 群类型 (Select: 公式群/知识群/羁绊群/工作流群)       │
│    - Members (Relation → 节点池 AV)                    │
│    - 阈值规则 (Text/JSON)                              │
│    - 统计快照 (Rollup from Members)                     │
└─────────────────────────────────────────────────────┘
```

### 9.2 群与 Tag 的关系（重新定义）

```
Tag 的新定位：
  ┌─────────────┐
  │  #Assassin   │ ← 用户打标签
  └──────┬───────┘
         │ 触发 On Create
         ▼
  ┌─────────────────┐
  │ 检查 L4 配置：    │
  │ #Assassin 关联   │
  │ AV "棋子数据库"   │
  └──────┬──────────┘
         │ 加入 AV
         ▼
  ┌─────────────────┐
  │ AV 中角色列 = ?  │
  │ → 填入 "刺客"    │
  └──────┬──────────┘
         │ 角色确定
         ▼
  ┌─────────────────────────┐
  │ L3 检查 AV + 角色 →      │
  │ 确定身份 → 挂载命令       │
  │ 同时：自动加入群           │
  │ "刺客羁绊" 的 Members     │
  └─────────────────────────┘
```

**总结**：Tag 是**入口触发器**，AV 是**身份源头**，群是**关系容器**，L3 是**行为决策器**。
