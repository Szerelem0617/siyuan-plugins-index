# 基于热 SQLite 表的完全虚拟重构与属性重定向调研报告

> **目标**：在不修改思源原生内核的前提下，探索以独立的「热 SQLite 表（Hot SQLite Table）」作为单一真理源，彻底接管 AV 数据库读写及块属性读写，并评估双模式回写（实时回写 vs 卸载时回写）与全域重定向的可行性与工程挑战。

---

## 1. 核心构想与技术可行性验证

### 1.1 核心机制：以 SQLite 为主控真理源
```
┌────────────────────────────────────────────────────────────────────────┐
│               IndexOS 纯热表架构 (Hot SQLite Source of Truth)          │
├────────────────────────────────────────────────────────────────────────┤
│                                                                        │
│   【前端交互 / 插件 / 视图】                                           │
│   • AV 表格 / 看板 / 画廊                                              │

│   • 块标属性面板 (Attribute Inspector)                                │
```

### 1.2 原生层面：能否将所有属性读写重定向到我们的热 SQLite 表？
**结论：在前端视口与插件生态内，100% 可以完全无感重定向！**

思源前端 Protyle 编辑器与所有原生 UI 交互，与后端的通信全部经过 `fetchSyncPost` / `fetchPost`（底层为 `window.fetch`）：
1. **属性读取重定向 (`/api/attr/getBlockAttrs`)**：
   * 拦截请求，如果目标块属于当前虚拟投影表，直接从热 SQLite 读取最新属性合并后返回，前端渲染立刻得到最新状态；
2. **属性写入重定向 (`/api/attr/setBlockAttrs`)**：
   * 拦截请求，直接执行 `UPDATE virtual_table SET ... WHERE id = ...`，阻止或延迟向物理磁盘写入；
3. **数据库渲染重定向 (`/api/av/renderAttributeView`)**：
   * 拦截请求，直接从热 SQLite 动态组装 `IAV` 视图数据返回；
4. **原生 SQL 查询重定向 (`/api/query/sql`)**：
   * 若查询包含虚拟表的属性，直接经由 IndexOS 的 SQL 引擎在内存 SQLite 中计算后返回。

## 2. 两种回写策略的技术可行性分析

| 回写模式 | 运行机制 | 适用场景 | 优势与风险 |
| :--- | :--- | :--- | :--- |
| **模式 1：实时异步防抖回写 (Debounced Realtime)** | 修改热 SQLite 表后，启动 1000ms 防抖计时器，将积攒的变更合并打包为 1 次 `BatchSetBlockAttrs` 写入物理 `.sy`。 | 日常频繁修改状态、拖拽看板。 | **优**：崩溃零丢数据，多端随时同步。<br>**劣**：若跨 100 篇文档，有轻微合并 I/O。 |
| **模式 2：关闭投影时统一回写 (Flush on Close)** | 在投影存在期间，物理 `.sy` 保持绝对干净（0 磁盘写入）；仅当用户点击“关闭虚拟投影”或手动点击“保存落盘”时，全量刷入磁盘。 | 极致性能追求、深度数据批处理分析。 | **优**：绝对 0 磁盘写放大，性能无敌。<br>**劣**：若思源非正常闪退，热数据需依赖本地日志恢复。 |

---

## 3. 该设计将面临的 4 大潜在挑战与解决方案

### 挑战 1：崩溃安全性（Crash Recovery）与断电防丢
* **风险**：若采用“模式 2（关闭时才回写）”，如果电脑突然断电或思源强制杀进程，内存热数据有丢失风险；
* **解决方案（持久化 WAL / 本地热表备份）**：
  * 热 SQLite 表不放在纯挥发内存，而是写入插件独立存储目录的 `indexos_hot.db`（或 IndexedDB）；
  * 即使思源闪退，下次打开时插件会立即比对时间戳，提示“检测到未落盘的热表数据，是否一键同步到文档本体”。

---

### 挑战 2：原生块引用动态锚文本（Dynamic Block Ref）的跨文档同步
* **风险**：如果用户在热表里修改了某个块的 `name`（块名称），而此时没有落盘到该块的 `.sy`，其他文档中对该块的引用锚文本（`((id 'name'))`）可能暂时不会刷新；
* **解决方案**：
  * 内置属性（`name`, `alias`）等直接影响双链引用的核心元数据，默认强制走模式 1 极速落盘；普通自定义属性（`status`, `priority`, `score`）则留在热表中。

---

### 挑战 3：跨标签与多实体混合关联（Multi-Tag Joins）
* **风险**：如果一个块同时被打上了 `#task` 和 `#project`，它会在两个不同的虚拟表中存在；
* **解决方案（正交实体表设计）**：
  * 底层不要为每个标签各建一张物理隔离的表；
  * 而是维护一张 **统一的全局实体属性大宽表（`entity_components`）**，每个标签只是这张大表上的一个 SQL 视图（`CREATE VIEW view_task AS SELECT * ...`），从而天生支持任意多标签混合 JOIN 与统一更新。

---

### 挑战 4：多 Tab / 分屏 Protyle 编辑器的视觉即时同步
* **风险**：当用户左右分屏，左边是 AV 表格，右边是任务正文文档；在左边改了状态，右边正文里的 Supertag 药丸如何不经过磁盘刷新就立刻变色？
* **解决方案（IndexOS 响应式组件总线）**：
  * 属性修改时，通过插件已有的 `SupertagRenderer` 向所有活动的 Protyle 视图派发 DOM 更新事件，原地替换右侧正文块的药丸状态，完全绕过磁盘重载。

---

## 4. 调研最终结论

1. **完全可行，且具备极大优势**：
   通过 `window.fetch` 拦截网关 + IndexOS 热 SQLite 表，我们可以在 0 改动思源官方内核的前提下，**构建一个完全由 SQL 驱动的高性能虚拟数据中枢**；
2. **双模式回写是绝佳设计**：
   将回写控制权交给用户（默认开启“1s 防抖实时回写”保障安全，极客可切换为“关闭时手动回写”追求极致性能）；
3. **架构终局形态**：
   单人使用场景下，热 SQLite 表 + 统一实体组件视图，将让 IndexOS 兼具 **Excel 的自由、SQL 的强大算力、以及本地 Markdown 的安全持久化**！
