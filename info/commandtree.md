# 插件命令树管理与列表/数据库联动方案头脑风暴

针对“插件命令树管理（Command Tree Management）”这一新功能，本系统的核心目的是：**将庞大且零散的思源及第三方插件命令，通过直观的结构重新组织、按需过滤（白名单化）、分类、并配置个性化的激活方式。**
由于思源本身的系统命令含有大量对普通用户并不适用的底层或隐藏指令，所以“白名单化”与“分类整理”显得尤为重要。

结合你提供的两种思路，并基于思源 `AttributeView` (AV) 数据联动以及 `protyle-event` DOM 机制的底层现状，以下是对各种方案的深入对比分析及优化提议。

---

## 方案 1：全量固化命令大列表 + DB 配置驱动

**设计逻辑**：
一键向文档内压入一个巨大的 `List`，包含思源系统内部以及所有生效插件的全部可捕捉命令。
将这个列表通过底层属性设置为“强制只读/无法编辑”（锁定节点结构），然后在它的外层挂载并关联一个 `Database (Attribute View)`。用户的一切配置（如：标记启用/白名单、打分类标签、配置触发条件）全部在这个 Database 视图中通过“修改属性”完成。

*   **优点**：
    1.  **全局完备性无缝同步**：每次核心加载时比对刷新，只要系统有的，列表里绝对有，不会遗漏。对于那些喜欢浏览系统全景极客用户来说，这是他们的天堂。
    2.  **绝对的安全防篡改**：由于物理节点强制只读，杜绝了用户在列表层面瞎折腾（误删节点、拖乱层级导致关联崩塌）。一切配置通过 DB 维度的属性更新。
    3.  **UI 研发成本极低**：只需要做好 DB 视图（提供布尔列代表是否白名单，提供下拉选择列代表分类），不需额外写界面。
*   **致命缺点**：
    1.  **极端的性能灾难**：思源系统的命令动辄几百上千项。在单一文档生成上千个列表项并全部在同级渲染，极有可能直接卡死 `Protyle` 渲染引擎；更致命的是同时挂载上千行的 Attribute View 时，滚动和编辑体验难以想象。
    2.  **极差的信噪比 (Signal-to-Noise)**：90% 的底层系统命令用户一辈子都不会去绑定。逼迫用户在一片“垃圾数据”里勾选出几条白名单，是非常反直觉的设计。

## 方案 2：隔离双树机制 (系统源库只读树 + 用户自由配置树)

**设计逻辑**：
通过向文档压入两个顶级 List 项形成两棵大树：
1.  **第一棵子树（基准树）**：映射系统的所有命令与原生的默认分类，锁定为只读。这就是一个完整的内置指令字典。
2.  **第二棵子树（用户树/白名单树）**：用户可以从第一棵树自由地“拖拽/复制”命令列表项到第二棵树中。这棵用户树允许任意建立分类（子级 List）并直接与 Database 绑定。

*   **优点**：
    1.  **解决信噪比问题**：用户树完全是高度精简的白名单集合，只包含有用的命令命令，DB 的规模大大减小，清爽很多。
    2.  **物理心智模型优秀**：拖拽（Drag & Drop）极其直观，完美模拟了“从百宝箱抓取工具放到工具箱”的操作。
*   **致命缺点**：
    1.  **基准树依然存在性能拖累**：由于我们仍要生成第一棵巨大的“系统源树”，方案 1 中的大量 DOM 渲染卡顿依然存在。这相当于给文档拖了一个极其沉重的累赘包袱。
    2.  **跨树拖拽的脆弱性**：用户在跨树拖动 block 的时候，非常容易破坏插件对两个块的隐形绑定机制，或者直接弄丢关联属性 `data-node-id` 的正确性。而且如果系统删除了某条命令，用户树里拖过去的那个块成了永远的“幽灵”。

---

## 💡 方案 3：虚拟面板按需装配 + 单一用户结构树 + Database 深度管理 (推荐做法)

在仔细研读了思源 `src/features/data/list/action.ts` 和我们的 `Supertag` 强绑定 DB 机制后，我为你构思了第三种方案，它规避了上面两个方案的性能和交互问题：

**核心设计理念**：“永远不向物理文档写入垃圾数据（未生效的命令）。”

1.  **建立空白骨架**：
    用户使用斜杠命令 `/InitCommandTree` 时，插件仅在页面生成一个 **只属于用户的空列表**，且在下方**自动关联并初始化好一个 DB（按上一条的 Live View 瞬间创建默认列：启用开关、分类、触发热键）**。
2.  **虚拟系统的召唤层 (Command Picker Panel)**：
    不将系统命令树写入物理列表！而是在这个配置基准树旁边，提供一个专属按钮 `[ + 检索挂载系统命令 ]`。点击后，弹出一个极速的轻量化 Dialog (通过思源内部 API `commands/getTree` 并配以虚拟列表渲染)。面板内部天然就是按系统分类展开的树，并且支持高频快速搜索。
3.  **瞬间装配/注入**：
    在面板中，用户勾选想要的 5-6 个命令（比如特定的视图切换、一些高频快捷功能），点击确定。插件立刻通过 API `insertBlock` 将这几项精简地生成到真实的用户树中，并由于我们的联动机制，这几项自动在下方的 Database 中生成数据记录。
4.  **无拘无束的定制空间**：
    因为列表中所有的项目都是“经过准入筛选的白名单命令”，用户可以在这里像排版普通文本一样拖放、改变层级（用列表缩紧实现自定义的任意多级分类）。而 Database 视图紧随其后，为这些自定义好的命令赋予诸如“快捷触发”、“挂载到特定面板”甚至“Supertag 参数”。

### 为什么方案 3 最为优越？

*   **真正的零性能损耗**：弹窗中的虚拟 DOM 树（如类似思源的 `b3-list`）即使上万条命令滑动也不卡顿，因为**它们不进入文档实际结构（`blocks` 表）**。
*   **极致的干净整洁**：生成的文档中，只存在用户真正在乎的极少数心仪指令。不存在方案1、2必须背负的“大段只读字典废话”。
*   **契合现有技术栈**：这个方案能完美复用你已经写好的 `src/features/data/list/auto-update.ts` 结合 Database 的能力。用户树里就是一行行的 `ListItem` 绑着命令的 `data-cmd-id`，而下方的数据库记录属性——没有任何冗余。

---

### 下两步思考方向
如果你认同“向文档中写入大量不激活的命令是非常糟糕的性能反模式”，我们就可以集中算力在方案 3 的推演上：
1.  **如何可靠地获取全量命令？** 需要去挖掘思源 `window.siyuan.menus` 或是底层的注册字典，构建虚拟树结构。
2.  **命令的挂载锚点**：给写入物理文档的 List Item 注入特殊的 IAL (`custom-command-id="..."`)，以后这行列表文本无论怎么改，我们都能在 DB 中稳定执行这个真实的指令。

## 4. 优化体验：预设白名单 (Default Presets)

如你所见，如果用户初始化一个完全空白的树，面对几百个不知所云的系统命令可能会感到茫然。**“预配置”是提升 User Friendliness 的关键。**

当用户执行 `/InitCommandTree`（初始化命令树）时，我们不应只给一个空列表，而是**开箱即用**地注入一批“高频且实用”的核心命令组合，例如：
*   **📂 界面布局类**：切换侧边栏、切换双栏、全屏模式。
*   **🛠 工具类**：导出 PDF、字数统计、打开控制台。
*   **🧩 高频插件类**：如果检测到某些流行插件，自动提取一两个特色命令。

**心智模型**：这就像新买的手机预置了几个常用 App。用户一看就懂：“哦，这就是各种命令及其配置”，他们可以直接在这个基础上通过“弹窗面板”修改、增删，而不是从零开始搭建工具箱。

## 5. 核心架构：数据库字典与监控维度 (DB Schema)

既然决定用 Database 深度管理这条“白名单树”，我们需要考虑**要在什么层面上管控这些命令**。每一行指令在 DB 中除了物理关联，需要包含以下维度的字段构成：

### 核心标识字段 (隐式联动)
*   **CommandID (隐藏列/文本)**：核心锚点。系统和第三方插件的唯一命令标识符（如 `plugin-xxx:open-dialog`）。这个值不可被用户在视图中修改，由生成写入 IAL 时固化（`custom-cmd-id`）。

### 表现层字段 (显示与归类)
*   **Icon (图标)**：统一继承或用户自定义的命令入口图标。
*   **Name (主键/文本)**：命令的可读名称，初始从系统中提取，但**允许用户随意修改**（用户可能会为了自己好记，把“打开关系图”改成“看脑图”）。
*   **Category (单选/分类)**：命令的分组。尽管在 List 中可以通过父节点分组，但在 DB 中打上标签（如 `界面`, `同步`, `特定插件`），能更方便地跨层级聚合与过滤。
*   **Description (备注/长文本)**：记录这个命令是干嘛的，写给自己看。

### 状态管控与触发行为字段 (核心功能扩展)
如果我们要真正接管这些命令，以下属性是实现高级控制的基础：

*   **Enabled (复选框/启动状态)**：
    *   **作用**：有时用户不想从白名单彻底删掉这个命令，但暂时不想让它触发。取消勾选即可使其在此插件体系内失效。
*   **Show in Toolbar / Menu (复选框/挂载位)**：
    *   **野心**：我们可以实现一个全局“快捷执行悬浮窗”或“特殊动作面板”。勾选了这些字段的命令，会自动出现在这些高频入口中。这是**真正的“工作流定制”**。
*   **Custom Hotkey (文本/自定义快捷键)**：
    *   **作用**：绕过系统死板的快捷键注册，利用我们自己的事件拦截引擎，为特定命令分配“只在某几个场景生效”的局部热键或全局组合键。
*   **Payload / Default Args (对象字典/参数化执行，进阶探索)**：
    *   **作用**：某些高级命令如果支持带参数执行（比如 `Supertag` 召唤特定模板），可以在这里配置固定参数，使得同一个系统命令分裂为两个“不同参数配置”的用户定制行为。

这套数据库 schema 将普通的“思源命令快捷键面具”彻底变为一个**可视化、带状态管理、可自定展现位置的「命令中枢控制器」**。只要数据库视图捕获到了配置更改，我们就实时更新内存中的命令路由表，拦截并接管用户的操作。

## 6. 高阶探索：多步骤组合命令 (Macro / Advanced Commands)

在 Notion 或 Tana 中，强大的工作流往往不是由单一指令构成的，而是由一系列“动作（Actions）”有序排列执行的“宏（Macro）”。如果要在我们的体系中实现类似“组合命令”的功能（例如：点击一个自定义命令 `[晨间日记]` -> 系统自动新建文档 + 应用模板 + 展开侧边栏），我们面临如何配置和存储这组顺序逻辑的挑战。

基于现有的系统与数据库架构，这里头脑风暴并对比两种主流实现方案：

### 方案 A：关系字段强绑定 (Relational Approach)
**设计逻辑**：
将所有的单一原子命令视为基础库。如果用户想组合一个“宏命令”，他们在此树中新建一个节点（例如命名为“一键发文”），然后在这个节点的 Database 视图中，使用一个原生的 **`Relation (关联)` 字段或 `多选文本` 字段**。
用户通过关联字段，按顺序选入基础库中的命令项。
*   **优点**：
    *   **扁平化管理**：宏命令和单一命令在同一个列表中平级（或受相同的分组管理），它们在表单中表现一致，仅仅是这个“关联属性”有没有值。
    *   **完全利用原生 DB 能力**：没有跳脱出现有的表结构。
*   **缺点**：
    *   **顺序丢失风险**：思源默认的 `Relation` 字段在展示时可能不保留用户的点选顺序，而组合命令对执行顺序是强依赖的（必须先新建页面，才能运用模板）。
    *   **无法定义步骤参数**：如果两个步骤之间需要传递参数，或者需要设定“延迟 500ms 执行下一步”，单纯的关联关系完全无法记录这种“流（Flow）”元数据。

### 方案 B：子级列表流式编排 (Nested Flow Approach)
**设计逻辑**：
充分发挥列表系统本身自带**“层级（Hierarchy）和顺序（Order）”**的特性。
我们要创建一个“宏”，就在顶级列表建一个项起名叫“每日复盘（宏）”。然后将它需要的若干个原子系统命令，用子列表项（Indent）的方式挂在它的**下级**。

```markdown
- [组合] 每日复盘 （勾选了 Toolbar 显示，但没有具体 CommandID）
    - [执行] 切换侧边栏状态
    - [执行] 插入今日模板
    - [执行] 触发全局推流
```

*   **优点**：
    *   **直觉极强 (Highly Intuitive)**：这完美匹配了 Tana / Notion 中对宏逻辑的视觉表达形式——父子结构天生就代表了“包含性”，由上至下的列表顺序天生代表了“执行顺序”。
    *   **独立配参**：下级的原子命令也是一个完整的独立块，它在这个专属父级下拥有独立的 IAL 和 DB 记录，你甚至可以给第二步“插入今日模板”多配置一个“延迟执行 500ms”的局部属性，完全不会污染全局。
    *   **原生拖拽体验**：想调换宏命令里的执行步骤？直接按 `Alt + 上下方向键` 拖拽子列表项。这比在关系单元格里删了重配舒服 100 倍。
*   **缺点**：
    *   **命令复用的冗余**：如果不同的宏里用到了同一个系统命令，在这个体系下就变成了多行物理列表文本的复制（产生多个新 Block）。但这其实是可以接受的，因为这正是“实例（Instance）”的概念。
    *   **解析稍有复杂度**：插件在扫描数据库/树结构时，需要先判断当前行是一个“无 ID 的宏入口”，随后深入遍历由它包裹的所有直接子节点，构建出一个有序的 Execution Stack (执行栈)。

### 推荐结论：采用 方案 B（子级列表流式编排）

在思源这款基于 Block 的软件中，**用 Block Hierarchy 表达先后工序是绝配**。

方案 B 把“宏（Macro）”的概念从复杂的 JSON 配置剥离，变成了“可视化的流程清单”。
1.  **对于普通单条命令**：就是单独的一行，绑个 `CommandID`，简单直接。
2.  **对于高级用户**：你可以新建一个空行作为起始点（不绑 CommandID，打上一个叫 `IsMacro` 的勾），将其他基础命令拖到它下方作为子列表。当你触发这个父节点时，我们的插件负责按顺序遍历执行子节点。

这就把一款“快捷键工具”真正拉升为了**工作流编排引擎 (Workflow Orchestrator)**。这与“Supertag”的概念一样，都是基于“直观结构控制底层逻辑”的降维打击！
