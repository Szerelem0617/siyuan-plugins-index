# IndexOS 指令系统架构设计 (V2.0 — 4层模型)

该架构旨在将思源组件的操作逻辑从硬编码中剥离，转化为一种**基于本体论 (Ontology) 与面向对象 (OOP)** 的动态指令引擎，对标 Tana 的 Command 系统核心逻辑。

---

## 一、 核心分层架构

| 层次 | 名称 | 存储介质 | 核心定义 | 类比 (OOP) |
| :--- | :--- | :--- | :--- | :--- |
| **Layer 1** | **IndexOS Registry** (Command-Data) | 插件内置 JSON | 声明原子指令（内核 API、键盘模拟、JS 脚本）。不可拆解的最小执行单元。 | **原子指令集 / 系统调用** |
| **Layer 2** | **Logic Factory** (Command-DB) | AV 数据库 | 定义复合指令。配置内部参数流转（管道模式）与外部暴露接口。包含参数的标签、类型及 UI 提示。 | **函数定义 / 宏编排** |
| **Layer 3** | **Class Binding** (Type-DB) | AV 数据库 | 将命令挂载到特定 Supertag（类型）。配置“方法”与“属性列”的绑定关系（接线）。 | **类的方法挂载 (Method Binding)** |
| **Layer 4** | **Instance Data** (TypeSpecific-DB) | AV 数据库 | 存储具体块实例的属性数值。执行时作为参数的数据来源。 | **对象实例属性 (Object Properties)** |

---

## 二、 详细定义

### 1. IndexOS Registry (原子库)
*   **职责**：Source of Truth。定义如何与思源后端通讯。
*   **数据模型**：
    *   `id`: 指令全局唯一标识。
    *   `dispatch`: 执行方式 (api | keyboard | global | script)。
    *   `schema`: 描述该原子操作所需的原始参数结构。
*   **特性**：用户不可见，不可在此层编写业务逻辑。

### 2. Command-DB (逻辑定义与复合层)
*   **职责**：实现指令的“人话化”与“组合化”。
*   **核心功能**：
    *   **复合编排**：支持将多个原子指令 ID 串联为序列。
    *   **内部透传**：配置 `Step[n].output` 如何进入 `Step[n+1].input`。
    *   **接口暴露**：标记哪些参数需要由“调用者”提供（外部参数），哪些参数是“交互式”获取（Interactive）。
*   **UI 意义**：为参数提供 Label (如“插入内容”) 和 Type (如“日期”)，驱动自动生成的输入表单。

### 3. Type-DB (接口映射层)
*   **职责**：决定“某类块（Supertag）”能进行什么操作。
*   **核心功能**：
    *   **方法挂载**：将 Command-DB 中的逻辑 ID 关联到特定类型。
    *   **参数绑定**：配置映射关系。例如：将命令要求的 `target_date` 接口绑定到数据库中的 `截止日期` 这一列。
*   **特性**：实现逻辑复用，同样的“归档”逻辑，不同的 Type 可以绑定不同的属性列。

### 4. TypeSpecific-DB (实例数据层)
*   **职责**：承载业务数据。
*   **特性**：它是命令执行时的“上下文池”。当指令被触发时，Dispatcher 会跳转到对应 ID 的此数据库，按绑定关系提取实时数值。

## 三、 关键设计哲学

### 1. 指令即数据 (First-Class Citizen)
指令不再是插件代码里的 `case...break`，而是存在于数据库中的可链接节点。用户可以通过修改数据库，在不重载插件的情况下改变操作逻辑。

### 2. 隐式 `this` 上下文
Dispatcher 永远携带 `CommandContext`（包含触发块的 DOM、ID、所在文档）。命令中未显式指定的参数，默认从“当前触发块”中获取，实现高度的自动化。

### 3. 管道 (Pipeline) 执行模型
执行引擎支持 `resolveVariables` 同步/异步解析。
支持变量注入路径：`{{system:date}}` -> `{{context:block_id}}` -> `{{attr:field_name}}` -> `{{parent:attr:field_name}}`。

---

## 四、 未来演进：智能构建器
该架构天然支持**可视化脚本编辑器**。
未来可在 `Command-DB` 层引入逻辑分叉（If/Else）与循环（ForEach），将思源的块操作从“手动批处理”提升为“逻辑流自动化”。

---

## 五、 深化建议：基于 AV 的数据驱动型 Pipeline 架构

为了实现低代码环境下的极致灵活性，建议针对以下三个核心逻辑进行“地基加固”：

### 1. 指令管道化 (Pipelining Implementation)
在 `Command-DB` 中支持数组形式的指令序列。执行引擎需引入 **Memory Bus (内存总线)**，允许后续步骤引用前序步骤的返回值。
*   **优势**：支持如“先创建文档 -> 获取新 ID -> 在新文档插入内容”这类具有时序依赖的复杂操作。

### 2. 虚拟槽位映射 (Virtual Slot Mapping)
在 `Type-DB` 的接线层，不仅支持物理列绑定，还应支持“计算占位符”。
*   **定义**：允许将 `{{parent.attr:title}}` 或 `{{self.id}}` 直接“接线”到 Command 要求的输入插槽中。
*   **优势**：打破了只能读取当前行数据的限制，实现了跨层级的属性透传。

### 3. 延迟绑定与 UI 生成器 (Dynamic UI Generation)
当指令标记为 `Interactive` 时，引擎不应直接报错，而是根据 `Command-DB` 里的参数类型定义（如 Enum, Date, BlockID），动态生成一个符合思源原生审美的输入对话框。
*   **优势**：在自动化流程中保留了必要的人工决策节点。

## 六、 架构对比与选择理由

在头脑风暴中，我们对比了三种潜在架构：

| 维度 | 方案 A：ECS 特征式 (混入架构) | 方案 B：DSL 宏指令 (文档脚本) | **方案 0 (选定)：AV 链路模型** |
| :--- | :--- | :--- | :--- |
| **核心逻辑** | 功能随标签走 (Mixin) | 文档即代码 | **数据链接逻辑 (Ontology)** |
| **交互门槛** | 中（需记忆标签组合） | 高（需学习专用语法） | **低（可视化的表格配置）** |
| **思源集成度** | 一般（脱离 AV 原生体验） | 低 | **极高（深度复用 AV 数据库能力）** |
| **逻辑复杂度** | 高 | 最高 | **中（通过可视化管道平衡）** |

**最终选择“方案 0”的理由**：
1.  **顺应用户直觉**：思源用户已经习惯了 AV 数据库。将“配置”放在 AV 里，用户可以像管理笔记一样管理逻辑。
2.  **利用 AV 的查询能量**：我们可以利用 AV 现成的过滤、排序和隐藏列能力来管理庞大的指令集。
3.  **确定性高**：基于类型的强绑定（Type Binding）比基于标签的松散混入（Tag-Mixin）更不容易产生逻辑冲突，保证了系统的鲁棒性。

---

## 七、 总结：地基的价值
通过这套 4 层架构，IndexOS 将原本扁平的“块属性”升级为了一个包含**数据 (Data)**、**类型 (Class)** 和 **行为 (Behavior)** 的三元系统。这不仅是插件的一项功能，更是为思源笔记引入了一套完整的插件级**对象运行时 (Object Runtime)**。
